# Java Interview Griller — Implementation Plan

Source spec: [`build-plan.md`](./build-plan.md). This document translates that spec into
buildable, independently-implementable phases.

## How to use this document

- Each phase is self-contained: a fresh Claude Code session should be able to open **only**
  this file (plus the codebase as it exists after prior phases) and implement the phase
  correctly, with no other context.
- Implement phases **in order**. Each phase states its dependencies explicitly.
- **Do not start a phase until the previous phase's Completion Report is filled in and its
  tests pass.** This is how continuity survives across sessions with no shared memory.
- At the end of each phase:
  1. Run all tests (existing + new) and confirm they pass.
  2. Fill in that phase's **Completion Report** block directly in this file (replace the
     `_Not started._` placeholder). Include: what was built, file list, decisions/deviations
     from this plan and why, any known gaps, and exact commands to run/test it.
  3. Do not touch git — the user handles commits/branches manually.
- Section 4 ("Shared Contracts") is the single source of truth for cross-phase interfaces
  (types, Zod schemas, DB schema, API contract). If a later phase needs to change one of
  these, update Section 4 in the same session and note the change in that phase's
  Completion Report — don't let contracts drift silently between phases.
- Per the build plan's most important rule (build-plan.md §51/§53): whenever a choice arises
  between more features and better interview quality, **choose interview quality**.

## 1. Architecture Overview & Key Decisions

The build plan mandates React/TS/Tailwind, a Cloudflare-compatible framework, Cloudflare
Workers, D1, and the Anthropic API, but leaves the exact project shape open. The following
decisions fill that gap. They are deliberately conventional/low-risk choices for this stack.
If you (the user) want something different, change this section before Phase 0 starts.

| Decision | Choice | Rationale |
|---|---|---|
| Deployment shape | **Single Cloudflare Worker** serving both the built SPA (via Workers static assets) and the `/api/*` routes | One `wrangler deploy`, no separate Pages project, no CORS between frontend/backend |
| Build tooling | **Vite** + `@cloudflare/vite-plugin` | Builds client + worker in one Vite config; `wrangler dev`/`deploy` integrate natively |
| Backend framework | **Hono** | Small, Cloudflare-native, first-class TypeScript, trivial to unit test via `app.request()` |
| Frontend routing | **React Router v6** (`createBrowserRouter`, SPA mode) | Client-side routing only, matches "no Node server" constraint |
| Validation | **Zod** | Required by build-plan §37/§48 |
| AI SDK | `@anthropic-ai/sdk`, called **only** from Worker code, never from the client | build-plan §36 |
| Package manager | **npm** | Universal, zero extra setup |
| Testing | **Vitest** for everything: `@cloudflare/vitest-pool-workers` for Worker/D1 tests, `jsdom` + React Testing Library project for components | Only combination that lets tests exercise real D1 bindings without a live Cloudflare account |
| IDs | `crypto.randomUUID()` | Unpredictable, no sequential IDs (build-plan §36) |
| Rate limiting | Cloudflare's native Rate Limiting binding where available, D1-based sliding-window fallback | No new infra dependency beyond what's already in the stack |
| Monorepo? | **No** — single npm package, folders separate client/worker/shared code | MVP scope doesn't justify workspace tooling |

## 2. Global Conventions

### Environment variables

Defined in `.dev.vars` locally (git-ignored; commit `.dev.vars.example`) and as Worker
secrets/vars in production.

```env
# AI
ANTHROPIC_API_KEY=
ANALYSIS_MODEL=claude-sonnet-5
INTERVIEW_MODEL=claude-sonnet-5
REPORT_MODEL=claude-sonnet-5

# Payments
PAYMENTS_ENABLED=false
LEMON_SQUEEZY_API_KEY=
LEMON_SQUEEZY_STORE_ID=
LEMON_SQUEEZY_VARIANT_ID=
LEMON_SQUEEZY_WEBHOOK_SECRET=
FULL_INTERVIEW_PRICE_EUR=9

# App
ENVIRONMENT=development   # development | production
FREE_ANSWER_LIMIT=3
```

Never hard-code model names or prices in application code — always read via
`src/worker/lib/config.ts` (built in Phase 0).

### Coding standards

- Strict TypeScript (`strict: true`, no `any` without a comment explaining why).
- No component/file over ~300 lines; extract before that.
- All D1 access goes through the `src/worker/lib/db/*` repository modules — no raw SQL
  elsewhere.
- All AI calls go through `src/worker/lib/ai/client.ts` — no direct `fetch`/SDK usage
  elsewhere.
- All external input (HTTP bodies, AI JSON responses) validated with Zod before use. Never
  trust model JSON output — validate, and on failure retry once with a corrective prompt,
  then fail gracefully (build-plan §37).
- No CV/JD/candidate-answer text in `console.log`/logs (build-plan §36). Log event names,
  IDs, counts, error types — never raw content.

### Testing conventions

- `npm test` runs everything; `npm run test:unit`, `npm run test:integration`,
  `npm run test:client` for subsets (exact scripts defined in Phase 0).
- Every phase that touches AI prompts must mock the Anthropic client in automated tests —
  no real API calls in `npm test` (build-plan §47). Real-API testing only happens via the
  manual CLI harness (Phase 5) or manual exploratory sessions, never in CI/automated runs.
- Integration tests that need D1 use `@cloudflare/vitest-pool-workers`'s isolated per-test
  D1 instance with migrations applied in `beforeAll`.

## 4. Shared Contracts

These are the canonical interfaces. Phase 1 implements them as Zod schemas + inferred TS
types in `src/shared/`. Every later phase imports from here rather than redefining shapes.

### 4.1 Technical Claim (build-plan §10)

```ts
// src/shared/schemas/analysis.ts
export const ClaimCategorySchema = z.enum([
  "JAVA", "SPRING", "MICROSERVICES", "DATABASE", "MESSAGING", "SYSTEM_DESIGN",
  "CLOUD", "DEVOPS", "OBSERVABILITY", "TESTING", "SECURITY", "PERFORMANCE",
  "ARCHITECTURE", "LEADERSHIP", "OTHER",
]);

export const TechnicalClaimSchema = z.object({
  id: z.string(),
  text: z.string(),
  sourceExcerpt: z.string(),
  project: z.string().optional(),
  category: ClaimCategorySchema,
  riskLevel: z.enum(["low", "medium", "high"]),

  reasoning: z.string(),
  likelyQuestions: z.array(z.string()),
  requiredDepth: z.enum(["basic", "intermediate", "senior"]),
});
export type TechnicalClaim = z.infer<typeof TechnicalClaimSchema>;
```

### 4.7 Database schema (D1)

Extends build-plan §31 with an `events` table (§43 analytics requirement) and an
`ai_usage` table (§38 cost-control requirement — the build plan asks for
`input_tokens`/`output_tokens`/`estimated_cost` fields but doesn't say where; a dedicated
table is used since usage is logged per AI call, not per row of the other tables).

```sql
-- migrations/0001_init.sql

CREATE TABLE interviews (
    id TEXT PRIMARY KEY,
    email TEXT,
    cv_text TEXT NOT NULL,
    job_description TEXT,
    analysis_json TEXT,
    interview_state_json TEXT,
    status TEXT NOT NULL DEFAULT 'created',
    paid INTEGER NOT NULL DEFAULT 0,
    free_answers_used INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    completed_at TEXT
);
CREATE INDEX idx_interviews_status ON interviews(status);

CREATE TABLE messages (
    id TEXT PRIMARY KEY,
    interview_id TEXT NOT NULL,
    role TEXT NOT NULL, -- 'interviewer' | 'candidate'
    content TEXT NOT NULL,
    evaluation_json TEXT,
    created_at TEXT NOT NULL,
    FOREIGN KEY (interview_id) REFERENCES interviews(id)
);
CREATE INDEX idx_messages_interview ON messages(interview_id);

CREATE TABLE reports (
    id TEXT PRIMARY KEY,
    interview_id TEXT UNIQUE NOT NULL,
    report_json TEXT NOT NULL,
    created_at TEXT NOT NULL,
    FOREIGN KEY (interview_id) REFERENCES interviews(id)
);

CREATE TABLE payments (
    id TEXT PRIMARY KEY,
    interview_id TEXT,
    provider TEXT NOT NULL,
    provider_order_id TEXT,
    amount INTEGER,
    currency TEXT,
    status TEXT,
    created_at TEXT NOT NULL
);
CREATE INDEX idx_payments_interview ON payments(interview_id);
CREATE UNIQUE INDEX idx_payments_provider_order ON payments(provider, provider_order_id);

CREATE TABLE events (
    id TEXT PRIMARY KEY,
    interview_id TEXT,
    event_name TEXT NOT NULL,
    metadata_json TEXT,
    created_at TEXT NOT NULL
);
CREATE INDEX idx_events_name ON events(event_name);
CREATE INDEX idx_events_interview ON events(interview_id);

CREATE TABLE ai_usage (
    id TEXT PRIMARY KEY,
    interview_id TEXT,
    request_type TEXT NOT NULL, -- 'analysis' | 'interviewer' | 'evaluator' | 'report'
    model TEXT NOT NULL,
    input_tokens INTEGER,
    output_tokens INTEGER,
    estimated_cost_usd REAL,
    created_at TEXT NOT NULL
);
CREATE INDEX idx_ai_usage_interview ON ai_usage(interview_id);
```

`interviews.status` values (build-plan §31): `created`, `analyzing`, `ready`,
`in_progress`, `payment_required`, `completed`, `failed`.

### 4.8 API contract (build-plan §32)

All request/response bodies are JSON, validated with Zod on the way in and out.

| Method & Path | Request body | Response body (200) |
|---|---|---|
| `POST /api/interviews` | `{ cvText: string, jobDescription?: string }` | `{ interviewId: string }` |
| `GET /api/interviews/:id` | — | `{ id, status, analysis?, interviewState?, paid, freeAnswersUsed, messages: Message[] }` |
| `POST /api/interviews/:id/analyze` | — | `{ status, analysis: CvAnalysis }` |
| `POST /api/interviews/:id/start` | — | `{ question: InterviewerResponse, messageId: string }` |
| `POST /api/interviews/:id/answer` | `{ answer: string }` | `{ nextQuestion?: InterviewerResponse, completed: boolean, paymentRequired?: boolean, interimSummary?: {...} }` |
| `POST /api/interviews/:id/report` | — | `{ report: Report }` |
| `POST /api/payments/checkout` | — | `{ checkoutUrl: string }` |
| `POST /api/webhooks/lemonsqueezy` | (Lemon Squeezy payload) | `{ received: true }` |

Error responses use a consistent shape: `{ error: { code: string, message: string } }` with
an appropriate HTTP status (400 validation, 402 payment required, 404 not found, 409
conflict/duplicate, 500 unexpected/upstream failure). Exact error codes are finalized in
Phase 8.

## Phase 1 — Domain Types & Zod Schemas

**Depends on:** Phase 0.
**Goal:** implement every schema in Section 4 (4.1–4.6) under `src/shared/schemas/` with
inferred types re-exported from `src/shared/types/`, plus focused unit tests. This is pure
data-shape work — no AI calls, no DB, no UI.

### Scope

- Create each schema file exactly as specified in Section 4. If real-world modeling forces
  a deviation (e.g. a field needs to be more permissive), make the change **and update
  Section 4 of this document in the same session** so later phases stay in sync — note the
  change in the Completion Report.
- `src/shared/types/index.ts` barrel re-exporting all inferred types.
- `src/shared/schemas/index.ts` barrel re-exporting all schemas.
- A small shared helper `parseOrThrow(schema, data, context: string)` used by the AI layer
  in later phases to validate model output and throw a typed `SchemaValidationError` with
  useful context (which request type, which field failed) — but never logging the raw
  `data` content if it might contain CV text (build-plan §36). Put this in
  `src/shared/schemas/parse.ts`.

### Testing requirements (unit)

For each schema, write both a valid-input test and at least one invalid-input test
(missing required field, wrong enum value, out-of-range number):

- `TechnicalClaimSchema` / `ClaimCategorySchema`
- `CvAnalysisSchema` (including with and without `jobMatch`)
- `InterviewerResponseSchema`
- `AnswerEvaluationSchema`, `ControllerDecisionSchema`, `EvaluationAndDecisionSchema`
- `InterviewStateSchema`
- `ReportSchema` (including with and without `roleFit`)
- `parseOrThrow`: valid data returns parsed value; invalid data throws
  `SchemaValidationError` with a message that does **not** echo the raw input.

- [ ] `npm run test:unit` covers every schema with valid + invalid cases, all passing.

## Phase 2 — AI Client Abstraction & Configuration

**Depends on:** Phase 0, Phase 1.
**Goal:** a single, well-tested wrapper around the Anthropic SDK that every later AI-driven
module (analyzer, interviewer, evaluator, report) calls through. Structured-output
extraction, retry-on-invalid-JSON, token usage capture, and model selection via config all
live here — once, not duplicated per module.

### Scope

`src/worker/lib/ai/client.ts` exports something like:

```ts
export type AiRequestType = "analysis" | "interviewer" | "evaluator" | "report";

export interface StructuredAiCallParams<T> {
  requestType: AiRequestType;
  model: string;            // resolved from config by caller, not hard-coded here
  system: string;
  messages: { role: "user" | "assistant"; content: string }[];
  schema: z.ZodType<T>;
  maxTokens?: number;
  interviewId?: string;     // for usage logging only, never logged content
}

export interface StructuredAiCallResult<T> {
  data: T;
  usage: { inputTokens: number; outputTokens: number };
}

export async function callStructured<T>(
  anthropic: Anthropic,
  params: StructuredAiCallParams<T>
): Promise<StructuredAiCallResult<T>>;
```

Behavior requirements:

1. Calls the Anthropic Messages API requesting the model produce JSON matching `schema`
   (use tool-use / a JSON-only instruction in `system` — pick one approach and document it
   in the completion report; tool-use forced-JSON via a single tool call is the more
   robust option and is recommended).
2. Parses the response, validates with `schema.safeParse`. On failure: retry **once** with
   an added corrective message telling the model exactly what was wrong (use the Zod error
   issues, not raw candidate content). If the retry also fails, throw a typed
   `AiResponseValidationError`.
3. On Anthropic API errors (timeout, 5xx, rate limit): retry with backoff up to a small
   fixed limit (e.g. 2 retries, matches build-plan §37 "Anthropic API timeout" /
   "network retries"), then throw a typed `AiRequestError`.
4. Returns token usage from the API response (`usage.input_tokens`/`usage.output_tokens`).
   Does not itself write to `ai_usage` (that's a DB concern — Phase 7/8 will call
   `recordAiUsage` after `callStructured` returns, using this result). Keep this function
   DB-agnostic.
5. Never logs `messages` content or the raw model response text — only request type, model,
   token counts, and error types/messages.

`src/worker/lib/config.ts` (extends the version from Phase 0): add typed getters for
`ANALYSIS_MODEL`, `INTERVIEW_MODEL`, `REPORT_MODEL`, and a helper
`getModelFor(requestType: AiRequestType): string` mapping `"analysis"` → `ANALYSIS_MODEL`,
`"interviewer"` and `"evaluator"` → `INTERVIEW_MODEL`, `"report"` → `REPORT_MODEL`.

### Testing requirements

All tests mock the Anthropic SDK client (construct a fake object with a `messages.create`
mock) — **no real network calls**.

- Successful call: mock returns valid JSON matching a trivial test schema → `callStructured`
  resolves with parsed `data` and correct `usage`.
- Invalid JSON on first try, valid on retry → resolves, and assert the retry request
  included corrective context.
- Invalid JSON on both tries → throws `AiResponseValidationError`.
- Simulated API error (reject) with retries exhausted → throws `AiRequestError`.
- `getModelFor` returns the right env var per request type, with config defaults applied
  when unset in dev.

### Acceptance criteria

- [ ] `callStructured` implemented with retry/validation/error behavior above.
- [ ] Zero hard-coded model name strings anywhere outside `config.ts` defaults.
- [ ] All tests mock the SDK; `npm test` still makes zero real API calls.
- [ ] Errors are typed classes (not bare `Error`), so callers can branch on error kind.

## Phase 4 — Interview State & Controller Logic

**Depends on:** Phase 1.
**Goal:** the non-AI "brain" that manages `InterviewState` (Section 4.5) — pure functions
for initializing state from a `CvAnalysis`, folding an `EvaluationAndDecision` into the next
state, and deciding whether enough evidence exists to stop (build-plan §19, §33). This phase
has **no AI calls** — it's deterministic state-transition logic the AI-facing modules in
Phase 5 will call before/after their prompts.

### Scope

`src/worker/lib/interview/state.ts`:

```ts
export function initInterviewState(analysis: CvAnalysis): InterviewState;

export function applyEvaluation(
  state: InterviewState,
  ctx: { claimId?: string; evaluation: AnswerEvaluation; decision: ControllerDecision }
): InterviewState;
```

`applyEvaluation` responsibilities (build-plan §14–§17, §19, §33):

- Push `claimId` into `testedClaimIds` if not already present and the decision isn't
  `CLARIFY`/`FOLLOW_UP` on the same claim (i.e., a claim is "tested" once it's had a
  substantive exchange, not on every single follow-up — use judgment, document the exact
  rule chosen in the completion report).
- Update `topicScores` per claim category using the evaluation's `technicalAccuracy`/
  `depth`/`specificity` etc. (define and document a concrete scoring formula — e.g. weighted
  average — since build-plan doesn't specify one exactly).
- Append to `strongAreas`/`weakAreas`/`redFlags`/`contradictions`/`conceptsToProbe` based on
  `evaluation.strengths`/`weaknesses`/`missingConcepts`/`redFlag`.
- Increment `candidatePatterns` counters — this requires signal from the evaluator about
  buzzword use / "we" language / vagueness / concreteness (Phase 5 must ensure the
  evaluator's structured output carries enough signal for this; if `AnswerEvaluation`
  (Section 4.5) doesn't cleanly expose "used excessive we-language" as a field, derive it
  heuristically here from `buzzwordRisk`/`weaknesses` content, and document exactly how).
- Increment `majorQuestionsAsked`.
- Recompute `estimatedCompletion` (0–1) from: number of high-risk claims tested vs. total
  high-risk claims, `majorQuestionsAsked` vs. target range (12–20, build-plan §19), and
  whether `decision.shouldComplete` was signaled.
- Set `activeClaimId` to `decision.nextTarget` when it resolves to a claim id, else leave/
  clear per a documented rule.

`src/worker/lib/interview/controller.ts`:

```ts
export function shouldCompleteInterview(state: InterviewState, analysis: CvAnalysis): boolean;

export function selectNextClaim(
  state: InterviewState,
  analysis: CvAnalysis
): TechnicalClaim | undefined;
```

- `shouldCompleteInterview`: true if the AI's `decision.shouldComplete` was true on the
  latest turn (caller passes that through — or this function purely encodes the
  build-plan §19 fallback heuristics: all high-risk claims tested, `majorQuestionsAsked >=`
  a configured max (e.g. 20), or `estimatedCompletion >= 0.9`). Document which signal wins
  when they disagree.
- `selectNextClaim`: picks the next untested claim to focus on when the AI's `NEW_TOPIC`
  decision doesn't specify one — prioritize `riskLevel: "high"`, then claims covering
  `jobMatch.interviewPriorities` if present, then remaining claims. Returns `undefined` if
  none remain (signal to complete).

### Testing requirements (unit, no AI, no DB)

- `initInterviewState`: given a `CvAnalysis` fixture, produces a state with empty
  tested/strong/weak arrays, `majorQuestionsAsked: 0`, seniority copied from analysis.
- `applyEvaluation`: table-driven tests covering — a strong concrete answer moves the claim
  toward `strongAreas` and raises the relevant `topicScores` entry; a vague/buzzword-heavy
  answer raises `candidatePatterns.buzzwordAnswers` and adds to `weakAreas`/
  `conceptsToProbe`; a `redFlag`-bearing evaluation appends to `redFlags`; repeated
  `FOLLOW_UP` on the same claim doesn't double-count it in `testedClaimIds`.
- `shouldCompleteInterview`: true when `majorQuestionsAsked` exceeds the configured max;
  true when all high-risk claims are tested and `estimatedCompletion` is high; false on a
  freshly-initialized state.
- `selectNextClaim`: prioritizes high-risk untested claims; falls back correctly; returns
  `undefined` when all claims tested.

### Acceptance criteria

- [ ] All functions are pure (no I/O), fully unit tested, deterministic.
- [ ] Every heuristic/formula that isn't fully specified by build-plan is explicitly
      documented (in code comments and the Completion Report), not left implicit.
- [ ] `npm run test:unit` passes.

## Phase 8 — API Routes (Hono Worker)

**Depends on:** Phases 2, 3, 4, 5, 6, 7.
**Goal:** wire everything into the HTTP API from Section 4.8, on Hono, with input
validation, the interview turn loop, and graceful error handling. This is where the
Interview Engine (Phases 1–6) meets persistence (Phase 7) and becomes a real backend.

### Scope

Routes in `src/worker/routes/interviews.ts`, mounted in `src/worker/index.ts`:

- `POST /api/interviews` — Zod-validate body (`cvText` required, length bounds from Phase 3;
  `jobDescription` optional, length bound); create interview row (`status: 'created'`);
  `logEvent('cv_submitted')`; return `{ interviewId }`.
- `GET /api/interviews/:id` — load interview + messages, return per contract; 404 if
  missing.
- `POST /api/interviews/:id/analyze` — if `status` already past `analyzing`, return existing
  analysis idempotently (handles refresh/duplicate calls, build-plan §37). Else call
  `analyzeCv`, persist `analysis_json` + `status: 'ready'`, record AI usage, `logEvent
  ('scan_generated')`.
- `POST /api/interviews/:id/start` — requires `status: 'ready'`; init `InterviewState`
  (Phase 4), call `generateQuestion` (Phase 5) for the first question, persist state +
  message (`role: 'interviewer'`) + `status: 'in_progress'`, `logEvent
  ('interview_started')`.
- `POST /api/interviews/:id/answer` — the core loop:
  1. Reject if interview not `in_progress`, or already `completed`/`payment_required`
     without payment (see Phase 11 for the exact gating — this phase can stub a simple
     "always allowed" check and Phase 11 tightens it, OR implement the full gate now if
     straightforward; either is fine, document which was chosen).
  2. Guard against duplicate submission (build-plan §37): if the latest stored message is
     already a `candidate` message for this exact turn (e.g. an idempotency key or simple
     "last message role" check), don't double-process — return the previously computed
     result. Document the exact mechanism chosen.
  3. Persist the candidate's answer as a `messages` row.
  4. Call `evaluateAnswer` (Phase 5), persist `evaluation_json` on that message, record AI
     usage.
  5. `applyEvaluation` (Phase 4) → new state; persist `interview_state_json`.

## Phase 12 — Lemon Squeezy Payment Integration

**Depends on:** Phase 8, Phase 11.
**Goal:** real checkout + webhook handling per build-plan §21, using D1's unique index from
Phase 7 for webhook idempotency.

### Scope

- `src/worker/lib/payments/lemonsqueezy.ts`:
  - `createCheckout({ interviewId, priceEur }): Promise<{ checkoutUrl: string }>` — calls
    Lemon Squeezy's API to create a hosted checkout session for
    `LEMON_SQUEEZY_VARIANT_ID`/`LEMON_SQUEEZY_STORE_ID`, passing `interviewId` as custom
    checkout data so the webhook can correlate back to the interview.
  - `verifyWebhookSignature(rawBody: string, signatureHeader: string, secret: string):
    boolean` — HMAC verification per Lemon Squeezy's documented scheme, using the raw
    request body (not re-serialized JSON, to avoid signature mismatches).
- `POST /api/payments/checkout` (`src/worker/routes/payments.ts`): loads interview, calls
  `createCheckout`, returns `{ checkoutUrl }`, `logEvent('checkout_started')`. 404 if
  interview missing; 400 if `PAYMENTS_ENABLED=false` (checkout shouldn't be reachable in
  that mode — decide and document the exact response).
- `POST /api/webhooks/lemonsqueezy` (`src/worker/routes/webhooks.ts`):
  1. Read raw body, verify signature via `verifyWebhookSignature` using
     `LEMON_SQUEEZY_WEBHOOK_SECRET` — reject with 401 on failure, **before** parsing/trusting
     any payload content.
  2. Parse the event; on a successful-order event, extract `interviewId` (from custom
     checkout data) and `provider_order_id`.
  3. `recordPayment` (Phase 7) — relies on the `(provider, provider_order_id)` unique index
     to make this idempotent: if `DuplicatePaymentError` is thrown, treat it as
     already-processed and still return `200 { received: true }` (Lemon Squeezy retries
     webhooks — duplicate delivery must be a no-op, not an error, per build-plan §37
     "duplicate payment webhooks").
  4. On first successful record: update `interviews.paid = 1`, and if `status was
     'payment_required'`, move it back to `'in_progress'`; `logEvent
     ('payment_completed')`.
  5. Ignore/acknowledge (200) event types that aren't relevant (e.g. non-order events)
     without erroring.
- Never trust any `paid` value from the client — this route is the **only** place that ever
  sets `interviews.paid = 1` (cross-check that Phase 11 didn't add a client-settable path).

### Testing requirements

  fails.
- Unit: `createCheckout` with a mocked `fetch` to the Lemon Squeezy API — asserts correct
  request shape (store/variant ids, custom data carrying `interviewId`), returns the
  checkout URL from the mocked response.
- Integration: full webhook flow against real test D1 — valid signed payload for a known
  `interviewId` → interview becomes `paid=1`, status transitions correctly, event logged;
  replaying the exact same payload a second time → still `200`, `paid` stays `1`, only one
  `payments` row exists (idempotency proof).
- Integration: invalid signature → 401, no DB changes.
- Integration: `POST /api/payments/checkout` with `PAYMENTS_ENABLED=false` → the documented
  rejection behavior.

### Acceptance criteria
